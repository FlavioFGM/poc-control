Personal tool (soon, a team tool) for running customer proofs-of-concept end to end: plan the
scope, extract the test plan, cross-reference it against a base of already-validated
procedures, and track execution with session notes, status, and client-ready summaries.

Owner: Gabriel (Solutions Architect, SUSE). The interface shell (menu, navbar, dashboard) is
available in **Portuguese, English and Spanish** via a single global language switch. AI-generated
content and the Executar PoC domain forms' underlying data stay in Brazilian Portuguese (pt-BR) by
design — see "Scope of the language switch" below.

## What it does

The app covers two halves of the same workflow, now unified in a single build/deploy:

### Executar PoC (run a PoC)

- Upload a PDF, paste free text, or import the JSON exported by the planner (see below) — Gemini
  reads it natively and returns a structured list of test items (`code`, `title`, `description`,
  `acceptance criteria`, `category`, `phase`).
- Review and edit the extracted list before running classification.
- **Traffic-light classification per item**: vector search against a base of validated
  procedures → Gemini confirms the match actually resolves the item → if there's no match, a
  web search (Gemini + Google Search grounding) looks for feasibility evidence. Green = a
  validated procedure covers it, yellow = feasibility evidence (or no evidence at all, as
  "yellow — low confidence"), red = explicit evidence it's unsupported. The flag is a
  suggestion; you can always override the color and the linked procedure.
- **Procedure knowledge base**: upload validated runbooks as HTML, indexed per section
  (`h2`/`h3`) with embeddings, so a match points at the right step rather than a whole document.
  Finishing an item lets you promote the steps that worked into a new validated procedure.
- **Sessions**: date, participants, agenda; status/notes/attachments per item, full status
  history.
- **Day roteiro**: tick the items you'll work on in today's session and generate a print-ready,
  ordered script with the linked procedures' steps already in execution order, preceded by this
  PoC's technical parameters (network, selected products) when they came from the planner's
  JSON export.
- **Session summaries**: paste a session recap (even one written by another AI tool) and Gemini
  organizes it into resolved points / open issues / next steps; from there it drafts a
  client-ready e-mail summary (copy button, no sending).
- **Client presentation / final report**: AI-written executive summary, a technical environment
  section (from the planner's parameters, when available), results by phase, and a session
  timeline — exported as a printable HTML page.
- Per-user Gemini API key (so usage bills to the engineer's own account) and per-user Gemini
  model override (free text — model availability depends on each account's plan).

### Planejar PoC (plan a PoC)

A 10-step guided wizard (project → products → infrastructure → network → credentials → ports →
architecture → tests → install → summary) covering sizing, network/IP planning, EIB image-builder
JSON generation, an architecture diagram, a port-readiness checklist, and a printable
client report / operator sheet. Originally a colleague's standalone static tool; now ported into
this app's own build (see "Architecture" below) so both halves share one deploy, one theme, and
one language switch. State is still kept in the browser's `localStorage` only — there is no
backend for the planner yet. Its "Export Project" button produces the JSON that Executar PoC's
"New PoC" screen can import directly.

## Scope of the language switch

One global PT/EN/ES switch, set once, applies everywhere in the UI shell and the Executar PoC
screens (buttons, labels, table headers, status chips) and to the planner wizard. It does **not**
translate: content generated by Gemini (summaries, classification rationale, executive
summaries — always written in Portuguese, since the audience is Brazilian customers), or data
typed by the user (item titles/descriptions, notes, procedure text). That data stays exactly as
entered, in Portuguese, regardless of the UI language.

## Architecture

| Service | Technology |
|---|---|
| `db` | PostgreSQL + pgvector (`pgvector/pgvector` image, ARM64), persistent volume |
| `api` | Python + FastAPI, SQLAlchemy + Alembic, `google-genai` SDK, background tasks for PDF/JSON processing |
| `web` | React + TypeScript (Vite), served by nginx, which also proxies `/api` |

Frontend is split by feature so the two halves can evolve independently:

- `web/src/features/executar-poc/` — this tool's own pages (PoCs, Procedures).
- `web/src/features/planejar-poc/` — a thin route wrapper (`pages/PlanPoc.tsx`) that embeds the
  planner. No planner logic lives here (see note below).
- `web/src/pages/` (Layout, Sidebar, Dashboard, Login, My account, Users) and `web/src/i18n.tsx`
  are the shell shared by both features.
- `api/` is 100% Executar PoC, plus three stateless endpoints the planner's optional connector
  calls (`api/app/planner/`).

**Note on the planner's internals**: the wizard itself — sizing tables, port requirements, EIB
JSON builder, architecture diagram, wizard state — is not part of this codebase at all. It lives
in the sibling `../poc-planner/` project (its own repo history, its own tests) as a single
self-contained `index.html`. This app never forks or re-implements it: `web/Dockerfile` copies
`../poc-planner/index.html` verbatim into the image at build time, nginx serves it at `/planner/`
(same origin as `/api`, so its session cookie and optional connector work), and `PlanPoc.tsx`
embeds that same URL in an `<iframe>` on the home route. An earlier version of this app carried a
hand-ported copy of the planner's logic (`plannerEngine.js`); it had already drifted behind
`poc-planner/index.html` and is gone now that there's one source to serve directly. See
`../poc-planner/docs/design-unification.md` (ADR 3) for the history of that decision.

- Embeddings: Gemini's embedding model, fixed dimension (`EMBEDDING_DIM` in `api/app/gemini.py`)
  to match the pgvector column — **not** user-configurable (unlike the text-generation model),
  since changing it would break the existing vector index.
- Search: cosine similarity in pgvector, top-k per item, then a Gemini confirmation pass (a match
  has to make sense, not just look similar).
- Login: single admin user today (seeded from `.env`), httpOnly session cookie, argon2 password
  hash. The data model already carries `user_id` everywhere so multi-user doesn't need a painful
  migration later.

## Running it

- `docker compose up -d --build` with a `.env` based on `.env.example`. The `web` image's build
  context is the repo root (`..`), not this folder, because it embeds `../poc-planner/index.html`
  verbatim — see `web/Dockerfile`. Running the command from inside this folder still works; just
  don't move `docker-compose.yml` without the sibling `poc-planner/` it reaches up to.
- Migrations run via Alembic (`docker compose exec api alembic upgrade head`).
- Deployed on a Raspberry Pi over SSH, `cloudflared` exposes only the `web` service externally
  (Cloudflare Access recommended on top of the app's own login).

## Roadmap

Planned next steps, in no particular priority order — added as they get planned, not all
committed to a date:

- **Multi-user collaboration**: today the data model already has `user_id` everywhere, but the
  app is single-user. Next step is real accounts working on the same PoCs concurrently without
  stepping on each other — ownership/visibility rules, and probably a backend for the planner
  (today it's `localStorage`-only, so two people can't share a plan in progress).
  - Clear authoring boundaries between Executar PoC and Planejar PoC so each can keep moving
    without the other blocking (already reflected in the `features/` split and CODEOWNERS).
- **Backend for Planejar PoC**: persist projects server-side (today: browser `localStorage`
  only), enabling direct hand-off from a plan to a PoC without manual JSON export/import.
- **Richer technical-parameter templating**: today the day roteiro shows the PoC's captured
  network/infra parameters as a reference block alongside the procedure steps. A deeper version
  would substitute placeholders inside the procedure text itself (e.g. `{{cluster_vip}}`) —
  requires authoring procedures with template tokens.
- **Model picker as a dropdown**: today the Gemini model override is a free-text field (since
  available models depend on each account's plan/key). A nice-to-have is listing models the
  current key actually has access to, instead of typing the name.
- Cloudflare Access in front of the public `cloudflared` endpoint (today: app login only).
- Automated restore-from-backup drill for the Postgres volume (today: backup script only).
